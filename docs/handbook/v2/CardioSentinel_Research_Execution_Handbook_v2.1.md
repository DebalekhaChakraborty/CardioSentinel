## Why this file is a pointer and not a copy

The blueprint arrived named as a handbook revision, and for a short time the same
1500-line document existed at two paths. Two identical copies answer the question
*which document governs future decisions?* with "either", which is the class of
provenance defect this repository is built to prevent. One canonical location was
chosen; this path became a pointer to it.

**No history was deleted.** The full text is in this file's own history at
`docs/handbook/v2/CardioSentinel_Research_Execution_Handbook_v2.0.md`, and its
content digest is recorded in
[`../../provenance/DOCUMENT_PATH_TRANSLATION_V3.md`](../../provenance/DOCUMENT_PATH_TRANSLATION_V3.md).

## Version

The filename now reads **v2.1**, matching the version the document's own header
declares. It was briefly named v2.0 while its header said 2.1; the header was not
downgraded to match a filename.

## What this does not change

`docs/handbook/v1/` remains authoritative for what the completed V1 programme
measured. The V2 line does not supersede v1.5. The split under `docs/handbook/`
is by **research programme**, not by recency.

## The accompanying `.docx`

`CardioSentinel_Research_Execution_Handbook_v2.1.docx` beside this file is a
rendered copy of the same blueprint, kept because every handbook revision in the
v1 line ships in both formats. **It carries no independent authority either.**
A binary cannot hold a pointer, so its status is declared here: where it and the
canonical blueprint disagree, the blueprint is correct.
